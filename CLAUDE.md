# CLAUDE.md

Guidance for AI assistants working in this repo. Keep this file short and current.

## What this is

**PRISM** — a store-operations platform for a sports-retail chain (Panatrade / "Fisik", "Factory Outlet"). Store staff run daily checklists, attendance, petty cash, handovers, and stock-transfer confirmations from a mobile web app; Ops/Finance/Audit/IT manage from desktop panels.

- Next.js 16 (App Router, React 19, React Compiler on), TypeScript strict.
- Postgres via **Drizzle ORM** + `pg` (node-postgres). Self-hosted DB — `DATABASE_URL` in `.env.local`.
- Auth: NextAuth (credentials). **Login is by NIK, not email.** Session user carries `id`, `role`, `employeeType`, `homeStoreId`, `areaId`.
- Deploy: VPS + PM2 + nginx (`ecosystem.config.js`, `deploy/`). Don't rely on the server's timezone — see the date convention below.
- Object storage: Biznet NOS (S3-compatible), `lib/storage.ts`. `lib/oss.ts` is legacy.
- Business Central (BC) OData integration for sales + stock transfers: `lib/bc/client.ts`, `lib/performance/business-central-*.ts`, `lib/db/utils/item-transfers.ts`.
- UI: Tailwind v4, Radix UI, `sonner` toasts, `lucide-react`. Indonesian-language user-facing copy.

## Layout

- `app/api/<role>/...` — route handlers, grouped by who calls them.
- `lib/db/schema/*` — Drizzle tables. `lib/db/schema/index.ts` re-exports everything + a `schema` object.
- `lib/db/utils/*` — per-task business logic (`briefing.ts`, `serah-terima.ts`, `store-opening.ts`, …). Task rows are created lazily via `getOrCreate*ForSchedule` when an employee opens the task — they don't all have to be pre-seeded.
- `lib/*` — cross-cutting helpers (`schedule-utils.ts`, `shift-tasks.ts`, `schedule-import.ts`, `performance/target-utils.ts`).
- `lib/performance/target-view.ts` — pure view logic for Ops **Performance Targets** (`/ops/performance-targets`): API types, store health bands (`on_track` / `watch` / `behind`, judged against elapsed days with today as half a day — that pace is **not shown** in the UI, Ops found it confusing), search + sort. UI lives in `components/ops/performance/*`; the list's filter/sort state in `useStoreListView`.
- `lib/user-import.ts` — IT Users bulk Excel import (`/it/users` → Import Excel). Reads the PRISM template **or** an HR roster (Employee No./Zona/Store Code/Organization Unit/Level/Status); unknown areas + stores are created (new stores default to the Daan Mogot placeholder location).
- `lib/attendance-health.ts` — the Ops **Attendance** (`/ops/attendance`) rule: rate = (present + late) ÷ (present + late + absent), **pending, Dinas and leave are left out**; ≥ 90% good, 75–89% at risk, < 75% critical, plus a "many late" tier with its own colour (fuchsia). Calendar, day panel and store detail all use it. Its month API (`/api/ops/attendance/overview?month=YYYY-MM[&storeId=N]`) is **read-only**: past no-record shifts inside the auto-absent window count as absent (what the cron will record). `GET /api/ops/attendance` (store day) is *not* read-only — it runs the auto-absent / auto-checkout fixers.
- **Attendance status names are defined once.** Words live in `lib/attendance-status.ts` (`ATTENDANCE_STATUS_LABELS`, `PENDING_LABEL` = "Pending", `ON_LEAVE_LABEL` = "On leave"); look + pieces in `components/status/AttendanceStatus.tsx` (`STATUS`, `AttendanceStatusBadge/Dot`, `AttendanceCountsLine`, `ATTENDANCE_COUNT_ITEMS`). Dashboard, Attendance, Stores and Areas all draw from them — never hand-write "hadir / belum hadir / not checked in / leave" or per-page colour maps. Counts go through `tallyPeople()` / `tallyStatus()` (`lib/attendance-health.ts`) so a status can't land in a different bucket per page — and **one status per person**: an employee with two schedule rows on a day counts once, as their best status (`pickDayStatus`: late > present > dinas > other leave > absent > pending), so "1 Present · 1 Late" can't be the same person twice (the dashboard, Stores, month overview and store-day tiles all use it; the schedules table has no unique user+day constraint); `/api/ops/stores` `attendanceSummary` is a full `AttendanceCounts` (`present` = on time only — use `showedUp()` for present + late). `dinas` is its own count; `excused` is **On leave** = Cuti / Sakit / excused only. Ops can set only **Dinas / Izin (`excused`) / Back-up** (`OPS_SETTABLE_ATTENDANCE_STATUSES`); Cuti / Sakit stay in the enum as legacy values. `backup` (migration 0028) = covering another shift (e.g. morning extended to full day) — no extra logic, just tallied as present. The Ops Dashboard's *Attendance by Store* rows also carry `noSchedule` — active `employee` users whose home store is that store and who have no `schedules` row **and** no `monthly_schedule_entries` row (OFF/leave count as planned) for today; it sits beside the counts (never in `total`), is drawn by `AttendanceCountsLine`'s optional `noSchedule`, and a store with staff but no shifts today has `rate: null`.
- **Status colours are defined once** (`lib/status-theme.ts`, client-safe): `TONES` is the palette (success emerald · danger rose · warning amber · late fuchsia · info sky · active indigo · leave violet · backup cyan · sick orange · verified teal · neutral/muted slate), each tone giving every look a page needs (`chip`, `soft`, `solid`, `dot`, `text`, `strong`, `ring`, `border`, `outline`, `tint`, `onDark`, `onDarkChip`, plus `TONE_HEX` for SVG). `ATTENDANCE_TONE` / `HEALTH_TONE` (attendance), `taskStatusTone()` / `storeProgressTone()` / `CELL_BOX` (task progress), `rateTone()` (≥ 80 green · ≥ 50 amber · else red — every completion bar) and `HEAT_STEPS` (% grids) map statuses to tones. Draw them with `components/status/AttendanceStatus.tsx` (employee app *and* Ops) and `components/status/TaskStatus.tsx` (`TaskStatusBadge`, `taskStatusTile`, `TaskStatusChip`, `RateBar`); the board square is `components/tasks/TaskCell.tsx`. **Never hand-pick emerald/amber/rose/… for an attendance or task status** — retune a colour in `status-theme.ts` and every page follows. (Visit Report keeps its own `tones.ts` for planning urgency; issues/petty cash/password-reset have their own maps.)
- **"Lupa password"** (`lib/db/utils/password-reset.ts`; shared rules + types in `lib/password-reset.ts`): login → `/forgot-password` (NIK + store email must match `stores.email` of the home store; the reply is identical either way) → IT **Reset Password** (`/it/password-reset`, sidebar badge) verifies and emails a one-time link (24h, only its SHA-256 stored) → `/reset-password/<token>` accepts only the requesting NIK — anyone else gets "Link ini bukan untuk NIK Anda.", 5 wrong NIKs lock the link. Emails (Indonesian, `lib/email/password-reset-emails.ts`) go via Microsoft Graph as `no-reply@panatradeprestasi.com` (`lib/email/graph-mail.ts`, `AZURE_TENANT_ID/CLIENT_ID/CLIENT_SECRET`, optional `MAIL_IT_NOTIFY_TO`); without them dev prints emails to the server console. The pages + `/api/password-reset/*` are public in `lib/auth/access.ts` (`isPublicPath`) but still CSRF-checked (only `isCsrfExemptPath` skips it). `stores.email` is IT-only: Store Management field, or bulk `npx tsx scripts/import-store-emails.ts data/store-emails.csv [--prod] [--apply]`.
- **Ops Petty Cash** is two Finance-style sheet pages (sidebar group + header tabs with "waiting" counts): `/ops/petty-cash/requests` (spending approvals) and `/ops/petty-cash/refills` (top-up approvals: what the store used + the refill it needs, rows open to the items); the bare `/ops/petty-cash` redirects. View logic `lib/ops-petty-cash.ts`, data `lib/db/utils/petty-cash-ops.ts`, shared UI `components/ops/petty-cash/shared.tsx`. A month there is when the request was **filed** (Jakarta), not `petty_cash_transactions.year_month` (the *period's* month — it lags for a store not yet refilled); requests still waiting on Ops show in every month. A refill's usage = completed items of the store's envelope (the period after its last *received* refill's month, else its first period); `refill = Rp 1.000.000 − balance`; a rejected request is frozen at its rejection time.
- **Petty cash Keterangan is always UPPERCASE** (`pettyCashDescription()` in `lib/petty-cash-categories.ts`): upper-cased while typing in the employee form, on save in `POST /api/employee/petty-cash`, and on every read (employee GET, Finance monitoring + transactions + Excel, Ops requests/refills) so rows written before the rule show the same way — no data migration. **Finance Petty Cash Monitoring** (`/finance/petty-cash`): a request row in a store's dropdown opens `components/finance/petty-cash/TxDetailModal.tsx` — receipt photo on the left in the zoomable `components/shared/ZoomableImage.tsx` (wheel zoom to cursor, drag to pan, double-click, rotate, reset), what the staff filled in (Keterangan, category, requested vs actual amount, who/when, OPS dates, rejection reason) on the right, ‹ › / arrow keys step through the store's requests. **Riwayat Koreksi Setoran** (`/it/setoran-correction/history` + `/finance/setoran-correction/history`, one shared `components/setoran-correction/SetoranCorrectionHistoryPage.tsx`; sidebar *Koreksi Setoran ▸ Koreksi / Riwayat Koreksi*): every correction/addition of every store from `getCorrectionHistory()` (`lib/db/utils/setoran-correction.ts`, API `/api/ops/setoran-correction/history` for IT and `/api/finance/setoran-correction/history`, optional `from`/`to` Jakarta days, capped at 5000 rows); search, period / store / petugas / jenis / role filters and column sort run client-side, rows open to before → after + the full note. No schema of its own.
- **Finance rejects petty cash requests** (`lib/petty-cash-review.ts` rules/states, `lib/db/utils/petty-cash-review.ts` logic; migration 0038 — columns on `petty_cash_transactions` (`finance_review` rejected → resubmitted → accepted, comment, snapshot) and `petty_cash_refill_requests` (`transfer_amount`, `rejected_count`, `rejected_amount`)): in the Finance Petty Cash Monitoring detail modal Finance can **reject a completed request** (comment optional) via `POST /api/finance/petty-cash/transactions/[txId]/review` `{action: 'reject'|'accept'}` — *accept* takes a rejection back or accepts PIC 1's correction. The request keeps `status = 'completed'` (its money is already off the period balance, and the balance goes back to Rp 1.000.000 with the refill regardless — the store absorbs a rejected amount); only the refill **transfer** leaves it out: `transfer = (1.000.000 − balance) − rejected (rejected + not-yet-reviewed resubmitted)`, computed live in `buildRefillRows` (`getOpsRefillRows` / `getRefillRowsByIds`, `OpsRefillRow.transfer`), shown on Finance's refill panel, and **frozen on the request when Finance clicks Verifikasi** (`verifyRefillRequests` stores it; Batal clears it). PIC 1 is notified of every rejection and the verify notification says how many requests were left out. PIC 1 (employee Petty Cash page) sees the rejection + comment on the request and can **Perbaiki & kirim ulang** (`POST /api/employee/petty-cash/[txId]/fix`: Keterangan, jumlah — the period balance moves by the difference — and/or a new receipt photo) → Finance accepts or rejects again. **Lock**: once the store's refill is verified after the request was filed (`getVerifiedCutoffs` → `isLockedByVerification`) Finance can no longer reject/accept it and a standing rejection is **permanent** — PIC 1 still reads it but can't correct it and files a new request next month. Migration 0038 is on staging; **PROD PENDING**. Ops refills page and the Finance Report still show the plain `max − balance`.

## Data model landmarks

- `areas` → `stores` (`storeNo` = the BC/POS code, e.g. `FF001`; keep separate from `name`).
- `users` (`nik` unique, `homeStoreId`, `areaId`) → `user_store_assignments` (assignment history; the schedule template roster reads this).
- IT "Delete user" (`lib/db/utils/user-deletion.ts`) always succeeds: personal records go (attendance, grooming, schedule, assignments, notifications, target shares); cash + shared history stays. If anything still references the user, the row becomes a hidden stub — `users.deleted_at` set, inactive, NIK renamed `<nik>~deleted~<id8>`. User lists that don't already filter `isActive`/store must add `isNull(users.deletedAt)`.
- One PIC 1 per store (the petty-cash holder) — flagged in red, not enforced (`lib/store-pic1.ts`): IT Users, Store Management, import review.
- Schedule: `monthly_schedules` (per store/`yearMonth`) → `monthly_schedule_entries` (per employee/day, OFF & leave included) → `schedules` (materialised working days only — `shiftId` NOT NULL).
- **Attendance is the only schedule lock** (`entryLocks()` / `lockedByAttendance()`): an import never touches an employee-day with attendance and replaces every other day, past or future; PIC imports are refused while the month has any entry without it (`blockIfUnattended`). Ops "Delete schedule" = *keep history* (default: only unattended days go) or *delete everything* (store code to confirm; attendance + task progress go) — the latter only while IT has the `schedule_delete_all` feature switch on (off by default; enforced in `deleteMonthlySchedule`, the preview returns `all: null` when off). Every schedule removal runs `removeSchedulesWithin()` in a transaction: day task rows deleted, Finance money rows (setoran, cek uang modal, store closing, cash counts) **unlinked, never deleted** (`schedule_id` NULL, migration 0025).
- `shifts` (`code` in `morning` / `evening` / `full_day` — stable; hours/breaks/accent live here).
- **Dinas shift** (`dinas`, roster code `D`, no hours/tasks): working outside any store. Scheduling it (Ops editor or Excel `D`) auto-records `attendance.status = 'dinas'` (`recordDinasAttendance` in `lib/schedule-utils.ts`). That auto row never locks the day — `lockedByAttendance()` ignores it and schedule deletes drop it; any other attendance row still locks. Counted as its own **Dinas** bucket in attendance counts (not folded into On leave), and left out of the rate.
- `shift_tasks` maps `shifts` → `task_definitions` (which task types a shift expects). Per-task tables in `lib/db/schema/tasks.ts`.
- Targets: `store_monthly_targets` (Ops sets one number) + `employee_monthly_targets` (fixed monthly %, `isPercentageOverridden` locks it) + `target_allocation_templates` (default % by headcount). Logic in `lib/performance/target-utils.ts`.
- `stores.status` (`active` / `close` / `ready_to_open`, `lib/store-status.ts` + `lib/db/utils/store-status.ts`) — only `active` stores record attendance, tasks, petty cash and appear in Ops/Finance progress rollups; `ready_to_open` is prep-only (schedules/targets, Rp 0 petty cash in Finance); change it only via `changeStoreStatus()` (IT-only; writes `store_status_history`, activation provisions petty cash; `checkStoreCloseReadiness()` is the future Audit hook). `stores.dept_code` = BC dimension code (`lib/store-dept-codes.ts`), IT + Finance views only — never return it from Ops/employee APIs.
- `item_transfer_orders` — 3-phase (Item Return → Shipping → Item Receiving) BC-driven pipeline. BC is pulled **company-wide** via `refreshTransferRegistry` / `refreshReceivingStatus` (`lib/db/utils/transfer-order-refresh.ts`: single-flight + throttled; light 14-day sweep, full 90-day + prune every 6h), driven by the **5-minute cron `/api/cron/transfer-orders`** (line in `deploy/crontab.example` — must be installed on the server); the employee page, badge poll and OPS page are throttled fallbacks. **Times**: BC's TO + receipt feeds carry only a date, so `returnDetectedAt` / `receivedAt` = when a sweep first saw it (accuracy = cron cadence); `droppingDetectedAt` = BC's shipment `systemCreatedAt`, and `returnDetectedAt` is clamped to ≤ it. "Still open" for a store is `returnOpenWhere` / `droppingOpenWhere` (`lib/db/utils/item-transfers.ts`) — the header badge (`pending-count`, `count(*)` only), the entry backfill and the notifications all use them. The OPS Transfer Order page's five timing metrics (Proses BC · WS → Foto Item Return · **Total Proses Item Return** = TO Dibuat → Foto Item Return · Delivery · Terima BC) are defined in `lib/transfer-order-metrics.ts` (pure; "Foto Item Return" = `returnSubmittedAt`; N/A for a DM origin; a photo taken before the WS shows as a negative duration; the API clamps "TO Dibuat" to ≤ WS / photo via `effectiveToCreatedAt`, since completed TOs leave BC's feeds and rows an old deployment wrote out of order can't be healed by a sweep). **TO Report** = three pages, one per process (`/ops/transfer-order/report/return|receiving|delivery`, sidebar *Transfer Orders ▸ Transfers / Item Return / Item Receiving / Item Delivery* + header tabs; the bare `/report` redirects to Item Return): per store, how many of that process it had in the period and how many are done, Harian/Mingguan/Bulanan like Task Progress, week/month rows carry a per-day trend strip, a row opens that store's TOs in a sheet, each item with its recorded timeline (`LegItem.steps` in `lib/transfer-order-report.ts`: Item Return **TO Dibuat → WS Diposting → Foto Serah Terima**, Item Receiving **Terima Fisik Barang di Toko → WR Diposting**, Item Delivery Foto Serah Terima → Terima Fisik, with the gap between steps). **Item Return** = one per TO for the origin store, counted on the TO Dibuat day, done = Foto Serah Terima; **Item Receiving** = one per TO with a WS for the destination store, counted on the WS Diposting day (it shows on the employee app from then, unchanged), but **timed only from Terima Fisik Barang di Toko** (the store's photo) and **done at WR Diposting** (`LegItem.anchorAt` / `startedAt` / `doneAt`; before the photo it is open with no clock — `StoreReport.notStarted`, "belum difoto" — and one BC closes with no store photo is done but has no duration, so averages divide by `timed`, not `done`); **Item Delivery** = the courier trip of a store → store TO, counted for the *destination* store on the day the origin submitted the Foto Serah Terima, done = Terima Fisik (a DM end gives no process on that side; a process belongs to the day it *started*). Rules in `lib/transfer-order-report.ts` (pure, `Process`/`PROCESS_META`), reads in `lib/db/utils/transfer-order-report.ts`, `GET /api/ops/item-transfers/report?process&startDate&endDate[&storeId]` (active stores only, Ops Area = own area, ≤ 31 days). It counts what is **in the table** — TOs BC completes without any store confirmation are deleted by the receiving/prune sweeps, so they don't appear (see the follow-up in memory `bc-item-transfers`). **Employee app**: the bottom nav is Home · Tasks · Attendance · **Transfer** (badge = open TOs, `useTransferPending()` in `lib/client/use-transfer-pending.ts` — one shared 60s poll for the nav, the Home Quick Action and the TO page) · Issues; Schedule moved into the floating More menu and Home ends with a "Jadwal Minggu Ini" week card (`WeekScheduleCard`, `GET /api/employee/schedule/week`, Mon–Sun in Jakarta); a transfer-order notification that arrives while the app is open also toasts (`EmployeeNotificationBell`). **Pushing is guarded**: the automatic sweeps (cron, page opens, badge polls) announce only when `NODE_ENV === 'production'` (or `TRANSFER_NOTIFY_DEV=1`) — a `next dev` pointed at the production DB must not message real staff — and IT can stop it with the `transfer_order_notifications` feature switch; tests call `notifyStoresOfOpenTransfers({ storeIds })` on the DUMMY-001 store only. A new open TO is announced **once per leg** to the staff scheduled today at that store as one grouped bell notification (`lib/db/utils/transfer-order-notifications.ts`; `return_notified_at` / `dropping_notified_at`, migration 0037) — in-app only, there is no OS/web push (no service worker) yet.

## Conventions

- **Dates for day-buckets** (schedules, attendance, task `date`) are Asia/Jakarta calendar days, and the DB holds two encodings of day D: `D-1 17:00:00` (Jakarta midnight — what the app writes, ~95% of rows) and `D 00:00:00` (UTC midnight — seed scripts). Read a bucket with `jakartaDateKey()`, query a day with `jakartaDayRange()` (`lib/day-bucket.ts`); never `getUTCDate()`, `toISOString().slice(0,10)` or an exact timestamp match. "Today" = `todayInStoreTimezone()` (`lib/schedule-utils.ts`). Real timestamps (`checkInTime`, …) use plain `new Date()`; show them with `jakartaTime()`. Both DBs run their session in Asia/Jakarta, so a `defaultNow()` timestamp reads back 7h off through Drizzle (which treats timestamp-without-tz as UTC) — set `createdAt: new Date()` explicitly on inserts whose time is shown.
- Neon-HTTP-safe DB style (a holdover): avoid `db.transaction()`; prefer `onConflictDo*` + batched inserts over SELECT-then-INSERT; keep `IN (...)` lists well under the Postgres 65535-param limit.
- Money is stored as integer Rupiah in `decimal`/`text` columns; format with `toLocaleString('id-ID')`.
- The staff (employee) app is Indonesian. Back-office panels mix English and Indonesian page by page — keep a page's language, but **one name per thing across Ops / IT / Finance**: take labels from the shared maps (issue statuses `STATUS_LABELS` in `lib/issues.ts`; petty cash `TX_STATUS_LABEL` / `REFILL_STATE_LABEL`; `STORE_STATUS_LABEL`; target health `HEALTH_META`; attendance as above; shift names = `shifts.label`). Setoran = *Uang diterima / Sisa kemarin / Wajib disetor / Disetor / Sisa*; Uang Modal = *Terhitung / Batas harian / Kurang dari batas / Belum penuh* (the staff app keeps its own words). Server/log strings and code are English.
- **Feature switches** (`lib/feature-switches.ts` declares each switch + default; `feature_switches` table, migration 0027; IT page `/it/feature-switches`, API `/api/it/feature-switches`): no row = default; check with `isFeatureEnabled()` (`lib/db/utils/feature-switches.ts`, fails closed to the default) on the server, not just in the UI.
- **Back-office pages are full width** (Ops / IT / Finance / Audit / PIC): no `mx-auto max-w-*` page containers (removed by request, 2026-10-21) — let grids/tables use the space; narrow forms go side by side (`xl:grid-cols-2`) instead. Dialogs, sheets and the employee phone app keep their widths.
- Store pickers/filters on IT pages use the searchable `components/shared/store-combobox.tsx` (pass `modal` inside a Sheet/Dialog).
- Ops pages that browse stores/orders/visits/issues use **list rows** (`components/ops/layout/OpsList.tsx`: `OpsList` + `OpsListRow`), not multi-column card grids. KPI tiles, calendars and form fields stay grids (Petty Cash is the exception — Finance-style sheet tables, by request). Their search / filter / sort bar uses `components/ops/layout/OpsToolbar.tsx` (`OpsSearchInput`, `OpsFilterSelect`, `OpsSortControl`, `OpsChipTabs`); lay rows out by container width (`@container` + `@4xl:`), not viewport — the Ops sidebar takes a quarter of the screen.
- Route handlers return `{ success: boolean, ... }` JSON; utils return `{ success: true, data } | { success: false, error }`.

## Commands


Run seed/migrate/probe scripts as `npx dotenv -e .env.local -- tsx <file>` (`@/lib/db` reads `DATABASE_URL` at import).

## Environments (staging → production)

`.env.local` holds **two** databases: `DATABASE_URL` = **staging** (the app, `db:migrate`, `db:seed`, `db:reset` all use it) and `PRODUCTION_DATABASE_URL` = production (only `scripts/migrate-prod.ts` reads it; the server has its own `.env.local` with just `DATABASE_URL`). Flow: change schema → `db:generate` → review SQL → `npm run db:migrate` (staging) → test → commit → `npm run db:migrate:prod -- --dry` → `npm run db:migrate:prod` (ships exactly the files staging already ran, in one transaction, refuses DROP/DELETE/TRUNCATE/type changes without `--allow-destructive`, rolls back if any table loses rows, you type the DB name to confirm) → deploy the code. Migrate prod *before* deploying. Destructive scripts (`db:reset`, `db:seed`, the `seed-*` one-offs) import `scripts/lib/not-production.ts` and refuse to run if `DATABASE_URL` is production. New staging DB: `npm run db:migrate && npm run db:seed:prod` (or `db:seed` for demo data).

## Working notes

- Don't commit or push unless asked. Branch off `main` first if you do.
- After editing `lib/db/utils/shift-lookup.ts`-cached data (shifts) via a reseed, restart the dev server.
- The hosted DB in `.env.local` is shared — `db:reset` wipes real data. Confirm before destructive DB ops.
- **Migration history got reset once** (old files deleted, `0000_lyrical_red_ghost` regenerated as a full baseline). `db:migrate` decides what to run purely by the journal `when` timestamp, so a fresh baseline looks "newer" than the DB and would re-`CREATE TABLE` everything. Fix / normal flow: edit schema → `db:generate` → review the SQL → `db:migrate`. If migration files ever get blown away again: `db:generate` (fresh baseline) → `db:baseline` (stamps every already-satisfied migration as applied without running it) → carry on. `db:baseline` is idempotent and finishes with a **column-drift report** (schema vs live DB).
- **Column drift** (a table exists but is missing a column the schema declares — e.g. `users.password_changed_at` was in the schema but never migrated, breaking every `SELECT`-whole-row on `users`): `db:generate`/`db:baseline` can't detect it (they diff snapshots, not the live DB). Fix: `npx drizzle-kit generate --custom --name sync_<thing>`, put `ALTER TABLE "x" ADD COLUMN IF NOT EXISTS "y" …` in the generated `.sql`, then `db:migrate`. `db:baseline`'s drift report lists these.
